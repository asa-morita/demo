# 体育祭 2026｜管理画面で更新する4チーム総当たり

Cloudflare Workers で公開する体育祭の予定・総合順位・対戦表です。
**Google スプレッドシートは使用しません。** 運営はサイトの `/admin` から大会データを編集し、Cloudflare Durable Objects（SQLite ストレージ）へ保存します。

## 画面

公開サイトの下部には **予定／総合順位／対戦表** の3タブがあります。
フットサル・バレーボール・バスケットボール・ドッジボールは4チーム・全6試合（各チーム3戦）の2チーム対抗総当たりです。綱引きは別形式で、2チーム合同の2組が対戦する全3試合です。試合は「第1試合」から「第6試合」で表示し、A vs Bから開始します。体力負担を抑えるため、隣接する試合で同じチームが続けて出場する回数を最小限にした順序です。対戦表はスマートフォンでも横スクロール不要の5×5表で、自己対戦の交点を斜線で表示します。

**借人競争も別形式**です。4チームが同時に競う回を4回実施し、各回の1〜4位を記録します。各チームの4回分の順位の合計が小さい順に競技順位を決定します。同点なら同順位です。

初期登録データ：
- チーム：Aチーム、Bチーム、Cチーム、Dチーム
- 競技（実施順）：**1. バレーボール → 2. バスケットボール → 3. フットサル → 4. ドッジボール** → 5. 綱引き → 6. 借人競争
- 2チーム対抗競技：4競技×6試合（計24試合）、**すべて「未開始」**で開始
- 綱引き：2チーム合同×2組の対抗戦を3試合、**すべて「未開始」**で開始
- 借人競争：全4回（第1〜4回）、**すべて「未開始」**で開始
- 開催枠：12:30〜18:00（開始・終了時刻や会場は各競技で別途設定）

### 管理画面（/admin）

管理画面は**画面最下部の固定フッター**から切り替えられる4つのタブに分かれています。iPhoneなどの小さな画面でも4つのタブを1列に表示し、画面の長い試合一覧をスクロールしていても切り替えできます。切り替え時には新しいタブの先頭へ戻ります。

| タブ | 機能 |
|---|---|
| **全体設定** | 総合ポイント表示／非表示、4チームの名称 |
| **競技・日程** | 6競技の名称・表示順・開始／終了時刻・会場 |
| **対抗戦結果** | 4競技の第1〜第6試合＋綱引きの第1〜第3試合、勝者・試合状態・コート・開始予定 |
| **借人競争** | **PR #8の全4回方式**：4チーム同時の順位入力、暫定順位と順位合計の確認 |

借人競争は対抗戦とは**別のタブ**で管理します。綱引きは「対抗戦結果」タブ内で2チーム合同形式の3試合を入力します。「対抗戦結果」には未終了の試合だけを表示する絞り込みと進行数を追加しました。

保存前にタブ・競技を切り替えたり再読込すると、入力破棄の確認が表示されます。誤って別タブへ移動しても、破棄確認でキャンセルできます。ほかの試合を保存するときは、編集中のフォームの内容を保持します。エラーや成功は画面下にも通知します。

管理者ログイン後に以下を編集できます。

1. **チーム名**：4チームの名称を変更。固定ID（A/B/C/D）と対戦組み合わせは保持します。
2. **競技情報**：競技名、表示順、開始／終了時刻、会場を編集。競技IDと6競技の枠は固定です。
3. **2チーム対抗試合**：試合状態（未開始／試合中／終了）、勝者、コート、開始予定を編集。終了時だけ勝者が必要です。
4. **借人競争**：第1〜4回の実施状態、4チームの順位、開始予定を編集。終了時には1〜4位を重複なく登録します。未開始・試合中では順位は空欄です。
5. **総合ポイントの表示／非表示**：管理画面の「総合順位のポイント表示」から切り替えます。表示時は合計ptの実数、非表示時は各チームの合計pt欄を `⁇?` と表示します。初期設定は表示です。

変更内容はそれぞれ保存ボタンを押すと永続化されます（ポイントの表示切り替えはボタンで即時保存）。総合順位のポイントを非表示にしても、内部でのポイント計算・順位・他の表示項目はそのままで、観客サイトの合計pt欄のみが伏せられます。別端末との編集競合は409エラーで通知し、再読込を求めます。観客の公開サイトは5秒ごとに情報を再取得します。ログインしていない利用者は公開情報の閲覧のみ可能です。

**注意：** Google Sheetsとの同期や旧シートからの自動移行はありません。以前のGoogleシートにのみ残っているデータは、必要なら切り替え前に確認し、管理画面から再入力してください。新しい保存先への切り替え直後、試合はすべて未開始です。**既存のDurable Objectデータは維持**し、従来の借人競争の2チーム対抗行は利用せず新しい4回分を追加します。今回の綱引きは新方式と旧方式の勝敗が互換ではないため、旧方式の綱引き6試合を `legacyTugMatches` として保存し、新方式の3試合を未開始で作成します。他競技の結果・日程・チーム名は保持します。

2026年10月28日の競技順変更は既存の大会データにも一度だけ適用されます。競技1〜4の表示順のみ指定した順に変更し、ドッチボールの旧表記はドッジボールに修正します。登録済みの試合結果、開始・終了時刻、会場、チーム名は保持し、その後の管理画面での順序編集も維持します。

## 2チーム対抗競技の総当たりの組み合わせ（綱引きを除く）

| 表示 | 保存用試合ID | 対戦 |
|---|---|---|
| 第1試合 | R3M1 | A vs B |
| 第2試合 | R3M2 | C vs D |
| 第3試合 | R2M1 | A vs C |
| 第4試合 | R2M2 | D vs B |
| 第5試合 | R1M1 | A vs D |
| 第6試合 | R1M2 | B vs C |

各チーム3試合で、連戦を完全には避けられませんが、連続する試合で同じチームが出場する箇所を最少の2箇所に抑えます。保存用IDは従来のままにして、登録済みの勝敗・開始予定を維持します。

4つの2チーム対抗競技では、勝数が多いチームを上位とし、2チーム同勝数なら直接対決で順位を決めます。3チーム以上が同勝数の場合は同順位です。6試合すべての結果が確定した競技のみ総合点に加算します。

## 綱引きの2チーム合同対戦（全3試合）

| 試合 | 2チーム合同の対戦 |
|---|---|
| 第1試合 | **A＋B vs C＋D** |
| 第2試合 | **A＋C vs B＋D** |
| 第3試合 | **A＋D vs B＋C** |

勝った側の2チームそれぞれに1勝を記録します。全3試合が終了した時点で、各チームの勝利数によって順位と総合ポイントを確定します。勝利数が同じチームは同順位で同じポイントを得ます（4競技の直接対決ルールは適用しません）。

## 借人競争の順位

借人競争は **第1回〜第4回** に4チームが参加します。各回の順位は1位から4位まで重複なく入力します。4回の順位合計（例：1位・2位・1位・3位なら合計7）を比較し、合計が少ないチームを上位とします。全4回が確定するまで総合点には加算しません。順位合計が等しい場合は同順位で同じ総合ポイントを加算します。

| 競技内順位 | 総合ポイント |
|---|---:|
| 1位 | 30 |
| 2位 | 20 |
| 3位 | 10 |
| 4位 | 0 |

## Cloudflare デプロイ

1. GitHub リポジトリ `asa-morita/demo` を Cloudflare Workers Builds に接続します。
2. ビルド／デプロイコマンドに `npx wrangler deploy` を設定します（既に接続済みなら通常のGitHub連動デプロイで更新できます）。
3. `wrangler.jsonc` で `TOURNAMENT_STORE` Durable Object を宣言しています。SQLite-backed namespace は初回デプロイ時のマイグレーションで作られるため、D1 IDやGoogle Cloudの設定は不要です。
4. Cloudflare の Worker → Settings → Variables and Secrets で **2つのSecret** を追加します。

| Secret | 用途 |
|---|---|
| `ADMIN_PASSWORD` | 管理者ログイン用パスワード（十分に長いもの） |
| `ADMIN_SESSION_SECRET` | Cookie署名用の別のランダムな秘密文字列（32文字以上を推奨） |

`SHEETS_SPREADSHEET_ID`、`SHEETS_CLIENT_EMAIL`、`SHEETS_PRIVATE_KEY`、`SHEETS_API_KEY` は不要です。Cloudflareに古い設定が残っている場合は削除できます。秘密情報をGitHubへコミットしないでください。

管理者セッションは署名付きHttpOnly Cookie（SameSite=Strict、HTTPS時Secure）で、8時間後に期限切れになります。管理APIでは認証・Origin確認・入力検証を実施します。ログイン失敗回数の制限はWorkerインスタンス単位のため、本番ではCloudflare WAF側でも `/api/admin/login` のレート制限を推奨します。

保存先は固定名 `festival-main` のDurable Objectです。値はデプロイやWorker再起動をまたいで保持されます。データを初期化したい場合は、ストレージを削除するのではなく運営画面で各試合を未開始に戻してください。

## ローカル実行・確認

```bash
npm install
cp .dev.vars.example .dev.vars
# .dev.vars に管理者用の2つの秘密を設定
npm test
npm run deploy:check
npm run dev
```

`http://localhost:8787/` が公開サイト、`http://localhost:8787/admin` が管理画面です。開発用Durable Objectはローカルに保存され、本番データとは独立しています。公開環境でストレージが利用できない場合は、誤ったデモ結果を見せないため `/api/results` が503エラーになります。
